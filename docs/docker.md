# Отчет по аудиту существующего кода и docker-контейнеров с предыдущих семестров

## 1. Обзор проанализированных решений предшественников

В рамках аудита были изучены исходные коды, конфигурационные файлы Docker и отчетная документация проектов предыдущих семестров:
1. **«Филиал бухгалтерии» (проект «ДокВайс»):** микросервисная архитектура на базе FastAPI и Docker. Логика парсинга построена на библиотеке `img2table`. Решение узкоспециализированное — ориентировано исключительно на табличные формы бухгалтерских документов (счета-фактуры, ТОРГ-12, УПД).
2. **«DataGang»:** клиент-серверный комплекс на C# (.NET / Avalonia UI). Модуль распознавания текста реализован на базе Tesseract OCR, извлечение реквизитов и классификация — через локальный инференс квантованной модели Gemma-3-4B (фреймворк Unsloth). Подготовлены базовые Dockerfile для инференса нейросети.
3. **«Крокант»:** настольный прототип на Python (Tkinter + Graphviz). Распознавание сканов выполнено на EasyOCR, построение связей предпринималось через вызовы локальной LLM (Ollama) с запросом вывода структуры в JSON.
4. **«radiator pigs»:** десктопное приложение на PyQt5 со специализированным парсером форматов (`fitz` / PyMuPDF, `python-docx`, Tesseract). Связывание тестировалось на семантических моделях RuBERT и SBERT, а визуализация графа — на библиотеках NetworkX и PyVis.

## 3. Выявленные слабые места исходного кода и архитектуры

1. **Неприменимость семантических языковых моделей для поиска связей по номерам:**
   * Эксперименты команды *radiator pigs* показали, что векторные модели (RuBERT, SBERT) размывают числовые токены. Модель считает номер договора (например, «№48-12») незначительным контекстом, из-за чего точность сопоставления связей падала до критически низких значений (множественные ложноположительные связи).
2. **Нестабильность вывода структуры данных от LLM:**
   * В решении команды *Крокант* локальная нейросеть при пакетном анализе регулярно нарушала синтаксис JSON, что приводило к сбою парсера и падению модуля построения графа.
3. **Эффект образования «суперкластеров»:**
   * Попытки связывания по нечетким критериям приводили к объединению несвязанных документов в одну гигантскую нечитаемую сеть, либо к полному исчезновению связей при ужесточении порога сходства.
4. **Блокировка интерфейса (отсутствие фоновой обработки):**
   * Все прототипы запускали распознавание документов синхронно в основном потоке приложения, вызывая зависание окна при обработке многостраничных файлов.

## 4. Рекомендации по расширению логики под требования заказчика

1. **Серверный фоновый конвейер обработки:**
   * Вынести модули OCR и классификации на сервер с поддержкой GPU. Реализовать асинхронную очередь задач (на базе Celery или встроенных BackgroundTasks FastAPI), что обеспечит комфортную фоновую обработку документов в пределах допустимых заказчиком 5–10 минут.
2. **Точный реляционный матчинг:**
   * Заменить семантический поиск сходства на точный поиск связей по цепочке атрибутов: распознанный тип документа, его собственный номер и дата, а также явные вхождения номеров родительских документов (ссылки на договоры и спецификации).
3. **Интеграция встроенного предпросмотра:**
   * Добавить в клиентский интерфейс компонент рендеринга документов (PDF, изображений и DOCX) непосредственно в рабочей области окна приложения рядом с панелью графа связей.

# Поддерживаемые типы и форматы документов, извлекаемые атрибуты

## 1. Назначение документа

Документ фиксирует:

1. Перечень форматов файлов, которые принимает система, и способ их обработки.
2. Классификатор типов документов, с которыми работает ИИ-конвейер.
3. Атрибуты, извлекаемые из каждого типа, с приоритетами (must / should / nice).
4. Правила валидации извлечённых значений.

Документ является входным для разработки модулей:

- `ingest` — приём и конвертация файлов;
- `ocr` — распознавание сканов;
- `classifier` — определение типа документа;
- `extractor` — извлечение атрибутов;
- `linker` — построение связей (см. документ `link_detection_rules.md`).

## 2. Поддерживаемые форматы файлов

### 2.1. Область MVP (обязательно к реализации)

| Формат | Расширения | Класс | Как обрабатывается | Модуль |
|:---|:---|:---|:---|:---|
| PDF с текстовым слоем | `.pdf` | Электронный | Извлечение текста напрямую (`PyMuPDF` / `pdfplumber`), таблицы — `pdfplumber` | `ingest` |
| PDF без текстового слоя (скан) | `.pdf` | Скан | Рендер страниц в PNG (300 dpi) → OCR | `ingest` → `ocr` |
| DOCX | `.docx` | Электронный | Парсинг `python-docx`: абзацы, таблицы, колонтитулы; встроенные изображения — в OCR | `ingest` |
| JPEG | `.jpg`, `.jpeg` | Скан / фото | OCR | `ocr` |
| PNG | `.png` | Скан / фото | OCR | `ocr` |

**Движок OCR:** Tesseract 5.x, языковые пакеты `rus` + `eng` (для смешанного текста — `rus+eng`).
**Предобработка изображений:** поворот по EXIF, бинаризация (Otsu), удаление шума, де-скев (deskew).

### 2.2. Направления расширения (после MVP)

| Формат | Расширения | Класс | Как обрабатывается |
|:---|:---|:---|:---|
| TIFF (многостраничный скан) | `.tif`, `.tiff` | Скан | Разбиение на страницы → OCR |
| DOC (legacy) | `.doc` | Электронный | Headless-конвертация через LibreOffice → DOCX → парсинг |
| XLSX (реестры, сметы) | `.xlsx` | Электронный | `openpyxl`, извлечение табличных полей |
| ODT | `.odt` | Электронный | `odfpy` |

**Вне области проекта:** аудио, видео, архивы, сообщения электронной почты (`msg`, `eml`), CAD-файлы.

### 2.3. Ограничения и допущения по форматам

- **Максимальный размер одного файла:** 100 МБ (настраивается).
- **Максимальное число страниц в PDF/скане:** 200 (настраивается).
- **Язык документов:** русский; допускается английский в реквизитах и реквизитных блоках.
- **Ориентация:** книжная и альбомная.
- **Качество скана:** не ниже 200 dpi, рекомендуется 300 dpi. При качестве ниже 150 dpi система ставит флаг «низкое качество распознавания».
- **Рукописный текст** не распознаётся на MVP; такие фрагменты помечаются как «не распознано».

### 2.4. Требования к локальности

- Все форматы обрабатываются **без обращения к интернету**.
- Модели OCR, классификации и извлечения атрибутов хранятся локально.
- Внешние API не используются.

## 3. Классификатор типов документов

Тип документа — обязательный атрибут (см. § 4.1). Классификация выполняется по трём признакам: (а) шапка/реквизиты, (б) лексические маркеры, (в) структура.

### 3.2. Приоритеты реализации

| Приоритет | Типы | Обоснование |
|:---|:---|:---|
| **P0 — MVP** | A1–A5, B1, B5, C1, C4, C5, D1, D3, E1, F1, F2 | Покрывают сценарий «НПА + договоры + акты + записки + регламенты»; позволяют проверить сквозной сценарий связывания по номеру |
| **P1 — первое расширение** | B2, B3, C2, C3, D2, D4, D5, E2, F3, F4 | Типичный документооборот организации |
| **P2 — дальнейшее расширение** | B4, E3, E4, G1, G2, H1, H2, I1, I2 | Финансы, кадры, проектирование |

### 3.3. Мультиклассификация и «неизвестный тип»

- Если документ содержит признаки нескольких типов (например, «Акт» и «Счёт» в одном PDF), допускается **мультиклассификация** (список типов с вероятностями).
- Если уверенность классификатора ниже порога (по умолчанию `0.55`), документ получает тип `U0 — Не классифицирован`, извлекаются только универсальные атрибуты, связи строятся по общим правилам (см. `link_detection_rules.md`, § 5).
- Пользователь может **вручную изменить тип** документа — это разрешено и учитывается при повторном связывании.

## 4. Атрибуты, извлекаемые из документов

### 4.1. Универсальные атрибуты (для всех типов)

| Атрибут | Код | Приоритет | Как извлекается | Валидация |
|:---|:---|:---|:---|:---|
| Тип документа | `document_type` | **must** | Классификатор (правила + ML) | Должен быть в справочнике § 3.1 |
| Регистрационный номер | `number` | **must** | Regex по шаблонам § 4.3 + контекст шапки | Соответствует шаблону типа |
| Дата документа | `date` | **must** | Regex дат § 4.4 + контекст | Валидная дата; не в будущем (по умолчанию) |
| Заголовок / предмет | `title` | **must** | Строка после вида документа до первого абзаца | Длина 5–500 символов |
| Орган / организация-автор | `issuer` | **should** | Шапка, подпись, колонтитул | Непустая строка |
| Подписант | `signatory` | **should** | Блок подписи | ФИО + должность (если есть) |
| ИНН организации | `inn` | **should** | Regex 10/12 цифр + контекст «ИНН» | Контрольная сумма |
| КПП | `kpp` | **nice** | Regex 9 цифр + контекст | — |
| ОГРН | `ogrn` | **nice** | Regex 13/15 цифр | Контрольная сумма |
| Статус документа | `status` | **should** | Лексические маркеры: «действует», «утратил силу», «проект» | Значение из справочника |
| Язык | `language` | **nice** | Определение языка | `ru`, `en`, `mixed` |

> **Правило:** если `must`-атрибут не извлечён, документ получает флаг `incomplete` и отображается в интерфейсе с предупреждением. Связи для такого документа строятся только по тем атрибутам, что удалось извлечь.

### 4.3. Формализованные шаблоны номеров

Используются для извлечения `number` и для разбора ссылок (см. `link_detection_rules.md`).

| Тип | Регулярное выражение (упрощённо) | Примеры |
|:---|:---|:---|
| Федеральный закон | `\d{1,4}-ФЗ` | `8-ФЗ`, `52-ФЗ` |
| Указ / постановление | `\d{1,5}` | `601`, `583` |
| Распоряжение Правительства | `\d{1,5}-р` | `1187-р` |
| Приказ министерства | `\d{1,5}(-[а-я])?` | `27`, `131н` |
| Приказ организации | `\d{1,5}(/\d{2,4})?(-[А-Яа-я0-9]+)?` | `12`, `45/2024`, `12-к` |
| Договор / контракт | `\d{1,6}(/\d{2,4})?(-[А-Яа-я0-9]+)?` | `45/2024`, `17-У`, `2024.001` |
| Доп. соглашение | `<номер_договора>-ДС\d*` | `45/2024-ДС1` |
| Спецификация | `<номер_договора>-СП\d*` | `45/2024-СП1` |
| Акт | `<номер_договора>-А\d*` | `45/2024-А1` |
| Счёт | `<номер_договора>-СЧ` | `45/2024-СЧ` |
| СТО | `СТО\s*\d{1,4}-\d{4}` | `СТО 12-2024` |
| Служебная записка | `\d{1,4}(/\d{2,4})?` | `12/2024` |
| Платёжное поручение | `\d{1,8}` | `12345` |

> **Важно:** шаблоны — стартовые. Для каждого типа допускается расширение списка через конфигурацию без изменения кода (YAML/JSON в `config/number_patterns.yaml`).

### 4.4. Формализованные шаблоны дат

| Формат | Regex | Примеры |
|:---|:---|:---|
| `DD.MM.YYYY` | `\d{1,2}\.\d{1,2}\.\d{4}` | `09.02.2009` |
| `DD.MM.YY` | `\d{1,2}\.\d{1,2}\.\d{2}` | `09.02.09` |
| `DD/MM/YYYY` | `\d{1,2}/\d{1,2}/\d{4}` | `09/02/2009` |
| `YYYY-MM-DD` | `\d{4}-\d{2}-\d{2}` | `2009-02-09` |
| «DD» месяц YYYY г. | `«?\d{1,2}»?\s+[а-я]+\s+\d{4}\s*г\.?` | `«9» февраля 2009 г.` |
| месяц YYYY г. | `[а-я]+\s+\d{4}\s*г\.?` | `февраль 2009 г.` |

Все даты нормализуются к ISO `YYYY-MM-DD`. При неоднозначности `DD.MM.YY` приоритет: `DD.MM.20YY` (для 00–49), `DD.MM.19YY` (для 50–99).

### 4.5. Приоритеты извлечения (сводно)

| Уровень | Значение | Что делать при отсутствии |
|:---|:---|:---|
| **must** | Без этого документ не может участвовать в связывании | Флаг `incomplete`; документ виден, но не связывается |
| **should** | Сильно повышает качество связей | Связи строятся, но с меньшей уверенностью |
| **nice** | Используется для отображения и уточнения | Связи не страдают |
